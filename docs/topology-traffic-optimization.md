# 拓扑后台流量优化

## 问题与实测依据

2026-10-29 对六个生产节点并行采样 180 秒，发现 cn 的 TUN 收发合计仅
0.34 KB/s，但 core 容器 eth0 接收 119.87 KB/s、发送 124.45 KB/s。容器接口
包含本机客户端和代理跳，不能直接当作公网计费流量，也不能与 TUN 数据相加。

随后在 cn 现有 Web 代理到 core 的五条 WebSocket 连接上被动统计 30 秒：

| 消息 | 双向正文 KB/s | 字节占比 |
| --- | ---: | ---: |
| 拓扑公告 | 47.09 | 75.3% |
| Raft 共识 | 11.94 | 19.1% |
| 转发包 | 2.99 | 4.8% |
| 校时请求与响应 | 0.55 | 0.9% |

拓扑公告约 109 帧/秒；359 个不同的 origin/generation 对应 3272 个拓扑帧。
抽样连接之外的 mTLS/WSS 未解密，该比例不代表全网比例。测量未暂停现有业务。

## 行为调整

- 普通 RTT/jitter 采样仍按原频率进行，结果立即进入本机邻接评分。采样只标记
  待发布状态，默认每 5 秒检查一次并合并发送最新的聚合质量。
- 发布前对照最近一次实际公告，而不是相邻两次测量。聚合内容不变时不重复
  广播；聚合成本变化继续使用既有阈值（绝对差至少 10ms，或相对变化至少
  25%；原值为 0 时新值至少 2ms）。逐步积累的小变化不会因每次变化较小而丢失。
- 同一 peer 的较差并行邻接变化，若未影响最终公告，不触发新的质量广播。
- 业务发送失败惩罚、恢复和探测降级/恢复继续唤醒发布循环，不等待 5 秒窗口。
  邻接加入/退出继续走原有即时结构发布路径。
- 泛洪不再回传至 ingress peer 的其他并行连接，也不回传至公告 origin；其余
  邻居仍收到公告。这个规则不新增发送确认、连接切换或每 peer 状态机。
- 默认 30 秒的完整周期刷新、新连接的缓存重放，以及旧进程版本拒绝规则保留。

协议格式、SDK、Raft 选举/心跳参数和线上配置均无需因本改动调整。由于仅调整
本节点发送行为，可与旧版本混合运行；完整流量收益需要各发布者都升级后重测。

## 可重复验证

`runtime_topology_replay_test.go` 使用相同事件序列回放 480 次有效探测响应，
覆盖 5 个邻居、每邻居 2 条连接及 6 个质量窗口。每个事件后排空异步发送队列，
避免把队列拥塞带来的合并误算为优化收益：

| 版本 | 拓扑帧 | 编码字节 |
| --- | ---: | ---: |
| 修改前 | 4500 | 763500 |
| 修改后 | 60 | 10200 |

该回放场景的帧数和字节数均减少约 98.7%；这是受控事件回放结果，不能直接
作为生产网络的节省比例。实时发布循环另有测试验证 100 次探测合并成一份最新
公告、未变的后续窗口不再发送，以及故障信号绕过长质量窗口。周期刷新、并行
传输来源排除、多跳收敛和节点重启由相应 mesh 测试覆盖。

```bash
GOWORK=off go test ./internal/mesh -run TestTopologyTrafficProbeReplay -count=1 -v
GOWORK=off go test -race ./internal/mesh -count=1
GOWORK=off go test ./... -count=1
```

本次先处理实测最大的拓扑开销。Raft 消息需要进一步区分具体类型后再评估；
不通过直接延长共识超时来降低流量。部署后应复用相同的接口和消息分型方法，
同时检查六节点状态、动态加入/断开、多路径恢复及业务延迟，再报告实际收益。
